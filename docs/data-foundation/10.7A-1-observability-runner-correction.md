## 1. Scope of the correction

The 10.7A runner (`run-canonical-read-only-audit.sh`) was rewritten (v1.1.0) so that, when a credentialed direct read-only connection is later available, observed results are recorded correctly. Bugs A–F below were identified by code review and by running the runner through mocked psql fixtures in success/partial/failure modes. Legacy 10.7A artifacts remain byte-identical to the committed set (verified 9/9 files).

## 2. Bugs fixed (A–F)

- **A — manifest written before run-state was known.** The manifest recorded access/success/failure state at startup, so a failing or no-access run could not be distinguished from a successful one. Fixed: the manifest and metadata are rewritten after the run state is known (`canonical_database_observed`, `direct_database_access`, `transaction_read_only_verified`, `exit_code`, `connection_used`).
- **B — exit-code gaps.** The runner conflated no-access and failure. Fixed: distinct exit codes `0` success / `1` failure / `2` no-access / `3` partial, driven by an explicit `RUN_MODE`.
- **C — verdict not derivable from the manifest.** The summary verdict was a hardcoded string. Fixed: the build script (`build-canonical-observability.py`) derives the verdict and per-section status from the actual run state (`A`/`B`/`C`).
- **D — SHA256SUMS only on success.** Checksums were written only on a clean run, so partial/failure outputs were unverifiable. Fixed: `SHA256SUMS.txt` is written on every exit (best-effort on failure) and excludes itself.
- **E — weak identifier validation.** Schema/table names were only checked against a list, so injected or malformed identifiers could pass. Fixed: real identifier validation `^[a-z_][a-z0-9_]*$` applied to schema AND table before any `count(*)` SQL is built; schema allowlist enforced per count; invalid identifiers produce a safe `error` record and the query is skipped.
- **F — count queries uncheckable in review.** Per-table counts were generated with string interpolation that mixed trusted and untrusted identifiers. Fixed: counts are exact `select count(*) from "schema"."table"` built only from validated identifiers, executed via stdin in the SQL file's own READ ONLY transaction.

Additional hardening (not lettered): connection URL only from allowlisted env vars with a `postgres(ql)://` prefix check; psql resolution with a fallback binary and a hard error if missing; SQL forbidden-statement gate at startup; raw per-file stdout/stderr captured under `raw/`; run state passed to the builder via env vars (`CC_MODE`, `CC_OUTDIR`, `CC_MANIFEST`, `CC_TXN_READONLY`, `CC_ACCESS`, `CC_FAILED_SQL_FILES`, `CC_FAILED_COUNTS`, `CC_API_PRIVATE_DB`).

## 3. Artifact naming

Two layout families are produced in the same output directory:

- **Canonical (observed-capable):** `canonical_schema_inventory.csv`, `canonical_table_counts.csv`, `canonical_country_entity_counts.csv`, `canonical_relationship_checks.csv`, `canonical_privilege_audit.csv`, plus `gap007_verification.json`, `api_private_observation.json`, `observation_summary.json`, `validation_report.json`. The `canonical_*` CSVs carry observed values when a connection is available and explicit `unavailable`/`error` states otherwise.

Checksums: `SHA256SUMS.txt` (replaces the 10.7A `SHA256SUMS`).

## 4. Run modes and expected state

| Mode | Trigger | Exit | Verdict | Canonical state |
|---|---|---|---|---|
| no_access | no allowlisted URL | 2 | B | `canonical_database_observed: false`, counts null/`unavailable` |
| success | all SQL files OK, read-only verified | 0 | A | observed counts, `transaction_read_only: true` |
| partial | some SQL files failed | 3 | B | observed sections preserved; failed sections `partial`/`error` |
| failure | read-only check failed or connection unusable | 1 | C | `canonical_database_observed: false` |

In every mode: `SHA256SUMS.txt` is written, the manifest/metadata reflect the true state, and the summary verdict is derived from that state.

## 5. Read-only guarantees

- Read-only enforcement: `BEGIN TRANSACTION READ ONLY; SHOW transaction_read_only; ROLLBACK;` must report `on` before any SQL file runs.
- Every SQL file executes via stdin inside its own READ ONLY transaction with `SET LOCAL statement_timeout='120s'`, `SET LOCAL lock_timeout='5s'`, always rolled back.
- Forbidden-statement gate at startup rejects write/DML/DDL/privilege statements.
- Count queries are exact `select count(*)` — never planner estimates.
- The runner has no write capability: it cannot run migrations, import data, or alter privileges/exposure.

## 6. Secret handling

- Connection is read only from allowlisted env vars `SUPABASE_DB_URL`, `DIRECT_URL`, `DATABASE_URL`, `POSTGRES_URL`; the URL must match `^(postgres(ql)?|postgres)://`.
- The URL is never printed, logged to artifacts, or embedded in the manifest/metadata (`secrets_printed: false`).
- The mock psql used by the test harness never reads or prints a URL.
- Artifact-level secret scan (connection strings, JWT-like tokens, service-role keys) passes.
